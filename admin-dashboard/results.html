What this page shows

The study compares three ways of scoring transactions for fraud with the same model: an external batch job that polls the database, scoring inside the database as each row is stored, and scoring in the application tier (the design this live demo uses). Every figure below comes from the study's benchmark scripts and result files; none is measured on this dashboard or on the live server.

Decision latency is the time from a transaction’s scheduled arrival to the moment its fraud score is saved, so waiting in a queue counts. The data are a public dataset of European card transactions used as a stand-in; they say nothing about fraud rates in Uganda.

How a transaction is scored

The prototype takes each transaction through the steps below. The three highlighted steps are the scoring, which is the part the study moves between architectures. The rule checks and the decision are not part of the benchmarks.

  1. Transaction arrivesThe amount, the time and 28 anonymized components, for a named customer.
  2. Customer history is readAverage amount, night-time habit and the last hour's activity, from the database.
  3. Three rule checksUnusually large amount, too many transactions in an hour, unusual time of day.
  4. Thirty features are builtTime of day, the 28 components and the amount.
  5. Four models score itXGBoost, LightGBM, a voting pair of those two, and an Isolation Forest.
  6. Weighted average35%, 35%, 15% and 15% give one fraud score from 0 to 1.
  7. DecisionBlock, review, monitor or allow, from the score and the rule checks together.
  8. SavedThe transaction, its score and decision are stored in the database.

Where the scoring step runs in each architecture

External batchThe transaction is saved unscored. A separate job checks every 10 seconds, reads the new rows out of the database, scores them and writes the scores back.
In-databaseA trigger inside the database scores each row as it is saved, so the data never leaves it.
Application tierThe application scores the transaction first, then saves it with its score. The live demo works this way.

All three use the same model and the same feature code, so only the place the scoring runs differs. To see the steps for one real transaction, use “Analyze a Transaction” on the dashboard.
