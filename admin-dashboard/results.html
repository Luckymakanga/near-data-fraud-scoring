What this page shows

The same fraud model was run three ways: as an external batch job that polls the database, in-database as each row is stored, and in the application tier (the design this live demo uses). This page shows what was measured and what the measurements do and do not show.

Risk ScoreOne transaction’s score out of 100, on the main dashboard.
Detection metricsHow well the model separates fraud from genuine payments over a whole test set (section 1). They do not depend on where the scoring runs.
Decision latencyHow long a decision takes to arrive (sections 2 to 4). It depends on where the scoring runs and does not change the scores.
More about this page

Every figure on this page comes from the study’s benchmark scripts and result files; none is measured on this dashboard or on the live server.

Decision latency is the time from a transaction’s scheduled arrival to the moment its risk score is saved, so waiting in a queue counts. The data are a public dataset of European card transactions used as a stand-in; they say nothing about fraud rates in Uganda.

In short

    This is a laboratory result on public data, from one laptop. A bank’s own rules may rule out running code inside its database, so the best choice for a bank can differ, and speed is only one of the things to weigh.

    How a transaction is scored

    The prototype takes each transaction through the eight steps below. The study measures how long it takes from step 1 to the moment the score is saved, and moves only the scoring (steps 4 to 6) between the three architectures. The rule checks and the decision were not part of the benchmarks.

    Moved between architectures Start or end of the timer Stand-in only Not in the benchmarks
    1. Timer startsTransaction arrivesThe amount, the time and 28 anonymized components, for a named customer. Decision latency counts from its scheduled arrival.
    2. Stand-in reads onlyCustomer history is readAverage amount, night-time habit and the last hour’s activity, from the database. The benchmarks only imitate this with stand-in reads, in the distance test (section 4).
    3. Not in the benchmarksThree rule checksUnusually large amount, too many transactions in an hour, unusual time of day.
    4. Moved between architecturesThirty features are builtTime of day, the 28 components and the amount, by one function shared by every architecture.
    5. Moved between architecturesFour models score itXGBoost, LightGBM, a voting pair of those two, and an Isolation Forest. Each gives a score from 0 to 1.
    6. Moved between architecturesWeighted averageWeights of 35%, 35%, 15% and 15% give one score from 0 to 1, shown on the dashboard as the Risk Score out of 100.
    7. Not in the benchmarksDecisionBlock, review, monitor or allow, from the score and the rule checks together.
    8. Timer stopsSavedThe transaction and its score are stored in the database. In the benchmarks the timer stops when the score is saved.

    Where the scoring step runs in each architecture

    External batchThe transaction is saved unscored. A separate job checks every 10 seconds, reads the new rows out of the database, scores them and writes the scores back.
    In-databaseA trigger inside the database scores each row as it is saved, so the data never leaves it.
    Application tierThe application scores the transaction first, then saves it with its score. The live demo works this way.

    All three use the same model and the same feature code, so only the place the scoring runs differs. To see the steps for one real transaction, use “Analyze a Transaction” on the dashboard.

      What these results do not show
